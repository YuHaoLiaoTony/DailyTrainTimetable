## Blocking

**B1｜過去的日期完全無法補檔，87 天缺口是結構性不可修補** — Blocking
- 證據：`Program.cs:96-97`（`startDate = today`、`Range(0, days)`）；`Program.cs:190` ParseDays 只接受正整數天數，無起始日參數
- 說明：程式只能產生「今天 + N 天」，08-23~11-16 不可能由現有程式碼產生；也沒有任何手動補檔指令或文件說明。
- 處置：新增 `--start-date`/`--from`（或補檔腳本）並在 README 明列補檔程序。

## Major

**M1｜排程常態只抓 1 天，latest.json 只宣告 1 天（不只快取命中時）** — Major
- 證據：`.github/workflows/update-train-data.yml:115`（`--days ${{ inputs.days || '1' }}`）；`Program.cs:134-137`
- 說明：冷快取或快取被淘汰時同樣只寫 1 天資料與 1 筆 availableDates，使用者端以 latest.json 當索引會看到資料集縮成 1 天。
- 處置：排程改抓固定窗口（例如 7 天）或讓 latest 以「掃描 output/data 現有檔案」為準，不依賴單次 run。

**M2｜每個日期都重新索取一次 OAuth token，請求量 ×2** — Major
- 證據：`Services/TdxAuthService.cs:20-32`（無 token 快取）、`Services/TdxApiService.cs:27`（每次 fetch 都呼叫）
- 說明：N 天 = 2N 次 HTTP 請求（31 天 = 62 次），直接放大停權風險，也讓 status-report「每日 ~1 次呼叫」的額度估算失準。
- 處置：token 依 `expires_in` 快取重用，並在 401 時強制重取一次。

**M3｜TDX 回傳空資料仍視為成功，且之後永久快取** — Major
- 證據：`Program.cs:108-114`（僅印錯誤仍加入 successfulDates 並寫檔）；`Services/DataCacheService.cs:60-65`（之後只判斷檔案存在）
- 說明：某日若取得 0 班車，該日會變成永久空檔，沒有任何機制會重抓或標記為可疑。
- 處置：空資料視為失敗（不寫檔、不進 successfulDates），或寫入 `empty: true` 標記並強制每日重試。

**M4｜快取沒有版本/更新時間比對，ForceFetchDates 永遠是空的** — Major
- 證據：`Services/DataCacheService.cs:24,69`（forceFetchDates 從未填充）、`Services/DataCacheService.cs:48-65`（只比對日期是否在 availableDates）；Program 未使用 ForceFetchDates
- 說明：README/status-report 宣稱會做「Pages 版本比對」、`docs/test-plan-cache.md` TC-4 宣稱會 `Re-fetching D1 (outdated)`，實際不存在；資料修正或 schema 變更時無法刷新既有日期。
- 處置：比對 `dataVersion` 與 `updatedAt`，不符即加入 ForceFetchDates，並讓 Program 處理該集合。

**M5｜排程被 disabled_inactivity 停用後，keepalive 無法自癒** — Major
- 證據：workflow `Refresh keepalive commit` 步驟（`update-train-data.yml:41-95`）位於同一個 `schedule` workflow 內；`README.md:187` 自承需 `gh workflow enable`
- 說明：60 天無 push → schedule 停用 → 唯一會 push 的步驟也永不執行，形成雞生蛋；`intervalDays=55` 只在「workflow 還會跑」時有效。
- 處置：改用獨立觸發源（外部 cron/PAT 排程 push）或加每日輕量外部探測，並在 M6 告警中涵蓋「schedule 停用」。

**M6｜87 天中斷沒有根因記錄，失敗完全靜默** — Major
- 證據：`docs/status-report.md:1,60-75`（最後更新 2026-06-17，只記錄 06-17 額度事件）；workflow `update-train-data.yml:107-127` 無 `if: failure()`／告警步驟
- 說明：08-23 之後停止的原因（額度、secret 過期、workflow 停用、程式錯誤）無從查證，導致「修好了沒」無法驗證。
- 處置：先在 status-report 補 08-22 之後的事件記錄與根因欄位，之後每次失敗都要留下可查連結。

**M7｜Pages 部署與 `dotnet test` 失敗會直接吞掉整個發佈，無回報路徑** — Major
- 證據：`update-train-data.yml:107-127`（test → generate → artifact → deploy 線性串接，無 `if: failure()` 分支、無通知）
- 說明：測試失敗或 TDX 失敗即中止，Pages 停留在舊資料且沒有人會知道（與已知問題 3 重疊，但這裡指的是 workflow 本身缺失敗處理）。
- 處置：加 `if: failure()` 的 issue/通知步驟，並把「資料日期落後天數」寫成 check 輸出。
